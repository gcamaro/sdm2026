Refinar com uma razão, uma mudança e uma comparação

Uma mudança no workflow precisa responder a um problema identificado.

Base no curso: slides 237–240; 312; 320; 322–338; 437–442.

No caderno da equipe

Um integrante quer aumentar o número de algoritmos. Outra sugere rever o domínio. A equipe volta ao caderno: o problema detectado é concentração dos registros e pouca avaliação em regiões distantes. Decide mudar uma escolha por vez e registrar o motivo.

Refinar não significa aumentar sempre a complexidade. Pode significar corrigir unidades, reduzir redundância, justificar uma área menor ou buscar um conjunto de teste melhor. Uma comparação útil mantém o objetivo e explicita o que mudou. A decisão precisa considerar plausibilidade, erros relevantes e estabilidade, além da métrica usada para seleção.

Sinal observadoVerificação ou ajuste possívelRisco da escolha
Muitos pontos agrupadosComparar filtro por célula e outra estratégia justificada.Eliminar informação rara junto com redundância.
Curvas biologicamente improváveisRever unidades, colinearidade, disponibilidade ambiental e flexibilidade.Confundir associação inesperada com erro sem investigar.
Boa média e partição fracaExaminar amostra e ambiente do bloco; buscar avaliação mais representativa.Escolher grade apenas pela maior nota.
Sensibilidade ao domínioComparar domínios apoiados em história e biogeografia.Escolher área para facilitar a discriminação.
Predição futura em ambiente novoAtivar e interpretar diagnóstico de novidade; considerar restrição da aplicação.Tratar clamping como solução completa.
Poucos registrosReduzir complexidade, considerar ESM e avaliar limites da informação.Confundir método mais simples com validação suficiente.

Ajustes existentes e extensões propostas

O script já prevê regularização, seleção de variáveis, partições espaciais, regras para composição do ensemble e alternativas comentadas de domínio. Os campos “antes” e “depois” do registro de refinamentos devem ser preenchidos com resultados reais apenas depois de executar e verificar cada alternativa.

best.models <- performance.models %>%
  filter(
    threshold == models.threshold,
    .data[[ensemble.threshold]] >= ensemble.cut,
    # round(.data[[ensemble.threshold]], digits = 1) >= ensemble.cut,
    thr_value > 0,
    thr_value < 1
  )

matching.models <- names(list.models)[unique(best.models$model_ID)]
matching.models

# Interrompe se nenhum modelo atender ao critério
if (length(matching.models) == 0) {
  stop("Nenhum modelo atingiu o critério definido para o ensemble.")
}

ens.models <- list.models[matching.models]

# Combina dois ou mais modelos; um único selecionado permanece modelo individual.
if (length(ens.models) == 1L) {
  ens.fit.model <- ens.models[[1]]
  warning("Apenas um algoritmo selecionado: a saída é um modelo individual, não um ensemble.")
} else {
  ens.fit.model <- fit_ensemble(
    models = ens.models, ens_method = ensemble.method,
    thr = models.threshold, metric = models.metric
  )
}

A mediana entre algoritmos reduz a dependência de uma superfície isolada, mas pode ocultar desacordos importantes. Mapear diferenças e conservar os componentes ajuda a entender essa variação. Um ensemble pode ter desempenho inferior ao de um modelo individual na aplicação; a vantagem precisa ser examinada.

Como registrar a comparação

Use um identificador para cada execução e um desenho de comparação coerente com a pergunta. Documente a razão da mudança, os parâmetros utilizados e os resultados por partição. Compare também a plausibilidade das curvas e dos padrões espaciais.

O resultado pode continuar inconclusivo

Se as alternativas plausíveis divergem e não há evidência para escolher, descreva a sensibilidade. Buscar mais dados pode ser um refinamento mais útil do que continuar ajustando parâmetros.

Exercício

Escolha um único sinal da tabela e escreva uma comparação executável: o que permanece igual, o que muda, qual evidência será comparada e que resultado justificaria manter a alteração.
